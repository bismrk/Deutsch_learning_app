# Тренажер німецької мови (Telegram Bot + Mini App) — Специфікація та технічний план

Цей документ фіксує повний продуктовий скоуп, архітектуру, схему бази даних, специфікацію LLM-інтеграції (DeepSeek), механіку генерації завдань (SQL + FSRS vs RAG), формули аналітики, систему тем оформлення та план навчання для реалізації тренажера німецької мови (рівні A1–B1).

## 1. Продуктовий скоуп та дорожня карта

### Фаза 1 — MVP (Фокус на вправах, FSRS і регулярності)

| Модуль | Прийняте рішення |
| ----- | ----- |
| **Архітектура інтерфейсу** | Гібрид: спільний API-бекенд + дві незалежні «вітрини» (**Telegram-бот** та **Telegram Mini App**). Модуль бота можна повністю вимкнути в майбутньому без змін у ядрі чи Mini App. |
| **Масштабування та ліміти** | Одразу закладаємо ізоляцію даних по `user_id` (готовність до швидкого розгортання на ~50+ користувачів) та денний ліміт викликів LLM API на користувача. |
| **Словник та імпорт** | Внутрішня БД слів. Користувач може додавати слова повідомленням або файлом прямо в бот, а також підключити власний **Google Sheet** для синхронізації. У MVP кожен користувач стартує зі своїм словником (підтримку спільних колод закладаємо в БД одразу). |
| **Алгоритм повторення** | **FSRS** (офіційна Python-бібліотека `fsrs`, як в Anki). Оцінку повторення (1–4) автоматично виставляє LLM за якістю відповіді. Режими старту: розумний мікс під рівень (A1–B1) за замовчуванням + кнопка ручного вибору граматичної теми. |
| **Типи вправ (4 типи)** | 1) Переклад речення (UA → DE) зі словами з бази; 2) Заповнення пропусків (артиклі, займенники, прийменники, *weil / als / wenn*); 3) Знайди й виправ помилку; 4) Об'єднай два речення в одне. |
| **Флоу тренування** | За замовчуванням 5 вправ у сеті (користувач може змінити кількість у будь-який момент). Вправи йдуть **по черзі з миттєвим фідбеком**: розбір помилок, граматичне пояснення та назва теми для пошуку на YouTube. Після 5-ї вправи — короткий підсумок. |
| **Статистика (Mini App)** | Інтерактивний спайдерплот зі шкалою від 0 до 100 (де 100 — впевнений B1) на **5 осей**: *Словник*, *Граматика*, *Стабільність* + *Шрайбен* і *Хьорен* (у MVP зі статусом «Скоро»). |
| **Теми оформлення (Mini App)** | Підтримка висококонтрастної **темної теми** (чорний фон, білий текст), **світлої теми** (білий фон, чорний текст) та режиму **Auto** (підхоплення системної теми Telegram) із синхронізацією між пристроями. |
| **Ритм і фідбек** | Щоденний FSRS-пінг (нагадування, скільки слів «дозріли» на повторення) + **тижневий звіт** (динаміка спайдерплоту «було / стало» + топ-3 слабкі теми для повторення на YouTube). |

### Наступні фази

* **Фаза 2 — Шрайбен, стартові бази та опційний `pgvector` (RAG):**
  * Модуль письма з екзаменаційними темами (A1–B1).
  * Перевірка від LLM за критеріями: граматика, структура листа/тексту, відповідність регістру (формальний / неформальний), правильність привітання та прощання.
  * Готові стартові колоди лексики рівнів A1–B1 (наприклад, за стандартом Goethe).
  * Опційне підключення розширення **`pgvector`** у PostgreSQL для семантичного групування слів і RAG-пошуку по базі екзаменаційних правил.
* **Фаза 3 — Хьорен і масштабування інтерфейсу:**
  * Вправи на аудіювання (Хьорен) по рівнях A1–B1.
  * За потреби — повне перенесення проходження вправ у Mini App і відключення бота.

## 3. Схема бази даних (PostgreSQL)

Усі таблиці спроєктовані з урахуванням ізоляції по `user_id`, підтримки спільних колод (Фаза 2) та майбутніх модулів Шрайбен/Хьорен.

1. **`users`**
   * `telegram_id` (`BIGINT`, PK)
   * `level` (`A1` / `A2` / `B1`, default `'A1'`)
   * `exercises_per_set` (integer, default `5`)
   * `theme` (`'system'` / `'dark'` / `'light'`, default `'system'`)
   * `sheets_url` (nullable text)
   * `reminder_hour` (integer 0–23, година щоденного пінгу, default `19`)
   * `timezone` (text, IANA-зона, default `'Europe/Kyiv'`)
   * `daily_llm_calls` (integer, default `0`, лічильник для контролю лімітів API)
   * `llm_calls_reset_date` (date, дата останнього скидання денного лічильника)
   * `created_at` (`TIMESTAMPTZ`)

2. **`decks`**
   * `id` (PK)
   * `owner_id` (FK на `users.telegram_id`, `NULL` для майбутніх спільних базових колод A1–B1)
   * `title` (text)
   * `level` (`A1` / `A2` / `B1` / `mixed`)

3. **`words`**
   * `id` (PK)
   * `deck_id` (FK на `decks.id`)
   * `word_de` (text, разом з артиклем для іменників)
   * `translation_ua` (text)
   * `part_of_speech` (text, optional)
   * `source` (`text` / `file` / `sheets` / `system`)
   * *(Фаза 2, опційно)* `embedding` (`vector(1536)` — для семантичного групування слів через `pgvector`)

4. **`user_word_fsrs`**
   * `user_id` (FK), `word_id` (FK) — складений ключ
   * `state`, `stability`, `difficulty`, `due_at`, `reps`, `lapses`, `last_review` (поля напряму мапляться на об'єкт `Card` із бібліотеки `fsrs`)

5. **`sessions`**
   * `id` (PK)
   * `user_id` (FK)
   * `mode` (`mix` / `topic`)
   * `target_topic` (nullable text)
   * `total_exercises` (integer)
   * `status` (`active` / `completed` / `abandoned`)
   * `created_at` (timestamp)

6. **`attempts`**
   * `id` (PK)
   * `session_id` (FK), `user_id` (FK)
   * `word_ids` (`JSONB` — масив ID цільових слів)
   * `exercise_type` (`translation` / `fill_blank` / `find_error` / `combine_sentences`)
   * `level` (`A1` / `A2` / `B1`)
   * `grammar_topic` (text)
   * `question_payload` (`JSONB` — згенероване завдання та прихований `reference_answer`)
   * `user_answer` (text)
   * `used_hint` (boolean, default `false`)
   * `is_correct` (boolean)
   * `grammar_score` (integer, 0–100)
   * `fsrs_ratings` (`JSONB` — оцінки 1–4 по кожному слову)
   * `youtube_topic` (text)
   * `created_at` (timestamp)

7. **`weekly_snapshots`**
   * `id` (PK), `user_id` (FK), `week_start` (date)
   * `vocab_score`, `grammar_score`, `consistency_score`, `writing_score`, `listening_score`
   * Зберігає історію спайдерплоту для порівняння прогресу в тижневому звіті.

## 4. Архітектура API та структура проєкту

### Основні ендпоінти FastAPI

Бот і Mini App звертаються до однакових ендпоінтів. Авторизація розділена за клієнтом:
* **Mini App** передає `Telegram initData` у заголовку `Authorization: tma <initData>` (бекенд виконує криптографічну HMAC-SHA256 перевірку підпису та свіжості `auth_date`).
* **Telegram-бот** передає внутрішній ключ `X-Internal-API-Key` + ідентифікатор користувача `X-Telegram-User-Id`.

* `GET /users/me` — отримання (або автоініціалізація при першому зверненні) профілю й налаштувань користувача.
* `PATCH /users/settings` — оновлення рівня (`A1`–`B1`), кількості вправ у сеті, теми інтерфейсу (`theme`: `system` / `dark` / `light`), посилання на Google Sheets, години нагадування та `timezone`.
* `GET /words`, `DELETE /words/{id}` — перегляд і керування власним словником (зі станом FSRS).
* `POST /words/import`, `POST /words/sync-sheets` — парсинг тексту, файлу або CSV із Google Sheets, дедуплікація слів та ініціалізація карток у `user_word_fsrs`.
* `POST /sessions/start`, `GET /sessions/active` — створення нової або відновлення активної сесії, підбір слів із найближчим `due_at`, вибір граматичної теми та генерація поточної вправи.
* `POST /sessions/{id}/hint` — видача підказки для поточної вправи з фіксацією `used_hint = true` на бекенді (античит).
* `POST /sessions/{id}/answer` — передача відповіді користувача в LLM, отримання розбору помилок + рейтингів FSRS (1–4) + теми для YouTube, оновлення `user_word_fsrs`, запис в `attempts` і підготовка наступної вправи (або підсумку сету).
* `GET /stats/radar` — розрахунок поточних показників 0–100 по 5 осях спайдерплоту + топ-3 проблемні граматичні теми за останні 14 днів.

## 5. Інтеграція LLM (DeepSeek), механіка генерації та розбір RAG

### 5.1. Конфігурація DeepSeek та захист від збоїв

Один повний сет із 5 вправ (генерація + 5 перевірок) споживає орієнтовно $6{,}000\text{–}10{,}000$ токенів. Навіть для 50 активних користувачів по 2 сети на день це $< 1\text{ млн}$ токенів/добу — менше $1\%$ від безплатної квоти у 100 млн токенів.

**Архітектурні правила для `llm_service.py`:**

1. **Провайдер-агностичність:** використовуємо офіційний `AsyncOpenAI` клієнт. Конфігурація виноситься в `.env`:
   ```env
   LLM_BASE_URL=https://api.deepseek.com
   LLM_API_KEY=your_key_here
   LLM_MODEL=deepseek-chat
   ```
   Щоб змінити DeepSeek на OpenAI, Gemini або OpenRouter у майбутньому, достатньо поміняти ці 3 рядки без правок коду.
2. **Вибір моделі під задачу:** у MVP використовуємо швидку чат-модель (`deepseek-chat`) для миттєвого фідбеку (1–3 сек). Важку reasoning-модель (`deepseek-reasoner`) залишаємо на Фазу 2 для глибокої перевірки великих листів *Schreiben*.
3. **Якість української мови та JSON:** у запиті передаємо `response_format={"type": "json_object"}`, проганяємо відповідь через Pydantic-модель (із 1 автоматичним retry при помилці парсингу), а в System Prompt додаємо 1–2 приклади природного фідбеку чистою українською, щоб прибрати кальки й русизми.
4. **Стійкість до RPM-лімітів:** безплатні тарифи часто обмежують кількість запитів на хвилину або мають короткі затримки. Обгортаємо виклик API у `tenacity` (exponential backoff + таймаут 20 сек).

### 5.2. Покрокова механіка генерації: як насправді працює пайплайн

Важливий інженерний принцип: **DeepSeek не «ходить» сам у базу даних і не перебирає всі твої слова.** Всю логіку відбору виконує наш Python-бекенд через звичайний SQL-запит, а в DeepSeek ми передаємо вже відібрані 1–3 конкретних слова.

**Покроковий шлях одного завдання:**

1. **Крок 1 — Відбір слів у PostgreSQL (Python + FSRS):**
   Бекенд робить швидкий SQL-запит до `user_word_fsrs` (виконується за $< 5\text{ мс}$):
   * Бере слова користувача, у яких уже настав час повторення (`due_at <= NOW()`), відсортовані за пріоритетом (спочатку прострочені та «проблемні» з високим `difficulty` / `lapses`).
   * Якщо «дозрілих» слів менше ніж потрібно — добирає нові слова (`state = New`).
2. **Крок 2 — Вибір типу вправи та граматики (Python):**
   Бекенд обирає один із 4 типів (`translation`, `fill_blank`, `find_error`, `combine_sentences`) так, щоб у сеті з 5 вправ вони рівномірно чергувалися, і підбирає граматичну тему під рівень (або бере тему, яку юзер задав вручну).
3. **Крок 3 — Збірка промпту (Context Injection):**
   Python підставляє ці 1–3 слова, рівень (`A1`/`A2`/`B1`), тип вправи і граматичну тему в готовий текстовий шаблон.
4. **Крок 4 — Виклик DeepSeek API:**
   DeepSeek отримує короткий чіткий запит (~300–500 токенів) і повертає одне готове завдання у форматі JSON.
5. **Крок 5 — Валідація та збереження:**
   Pydantic перевіряє структуру JSON. Завдання зберігається в `attempts` (разом із прихованим `reference_answer`), а користувач у Telegram бачить лише `instruction_ua` і `task_text`.

### 5.3. Чи потрібні векторна база та RAG? (Чесний розбір)

**Як працює RAG (Retrieval-Augmented Generation):**
Це патерн для пошуку за *змістом* у великих обсягах неструктурованого тексту (наприклад, 500 сторінок документації чи підручників). Текст ріжеться на шматки, кожен шматок перетворюється на масив чисел (**embedding / вектор**), і кладеться у векторну базу. Коли юзер ставить питання, система шукає *семантично схожі* шматки тексту й підкладає їх у промпт LLM.

**Чому для нашого MVP векторна база НЕ потрібна (і навіть шкідлива):**

| Критерій | SQL + FSRS (наш вибір для MVP) | Векторна база + RAG |
| ----- | ----- | ----- |
| **За яким правилом беремо слова?** | Строго математично: «які слова юзер ось-ось забуде по `due_at`» | Пошук за схожістю змісту (не знає про графік повторень) |
| **Точність і контроль** | 100% детермінована вибірка, ми точно знаємо ID кожного слова | Імовірнісний пошук, складніше гарантувати покриття словника |
| **Складність і витрати** | Нуль зайвих сервісів, миттєві SQL-запити, безплатно | Потрібна окрема модель для генерації embeddings + індексація при кожному додаванні слів |

**Де твоя ідея з векторною базою справді «вистрілить» у Фазі 2 (через `pgvector`):**

Не треба піднімати окремі бази типу Pinecone — у нашому PostgreSQL достатньо увімкнути розширення **`pgvector`**. Це дасть два круті апгрейди, коли MVP вже працюватиме:

1. **Семантичне групування слів у речення:** якщо по FSRS сьогодні «дозріло» слово `der Zug` (потяг), то замість випадкового другого слова `der Kühlschrank` (холодильник), векторний пошук знайде серед інших «дозрілих» слів семантично близькі — наприклад, `die Verspätung` (затримка) або `der Bahnhof` (вокзал). Тоді речення від DeepSeek виходять максимально живими й природними.
2. **Справжній RAG по граматиці й екзамену Goethe (для *Schreiben*):** у `pgvector` завантажуються перевірені конспекти з граматики та офіційні критерії оцінювання Goethe A1–B1. При перевірці листа бекенд дістає потрібні правила і підкладає їх DeepSeek, щоб модель перевіряла строго за стандартом екзамену без вигадок.

### 5.4. Генерація вправи: JSON-схема та правила

**JSON-схема відповіді LLM (Structured Output):**

```json
{
  "exercise_type": "translation",
  "level": "B1",
  "grammar_topic": "Nebensätze mit weil",
  "target_word_ids": [14, 29],
  "instruction_ua": "Переклади речення німецькою, використавши слова зі свого словника:",
  "task_text": "Я запізнився на зустріч, тому що потяг мав затримку.",
  "hint_ua": "Пам'ятай про порядок слів після сполучника weil (дієслово в кінці).",
  "reference_answer": "Ich habe mich zum Treffen verspätet, weil der Zug Verspätung hatte."
}
```

**Правила в System Prompt генератора:**

1. Природна жива німецька без дослівних кальок; уся допоміжна лексика поза `target_words` не перевищує `user_level`.
2. Специфіка 4 типів:
   * `translation`: `task_text` українською, вимагає використати всі `target_words`.
   * `fill_blank`: `task_text` німецькою з 1–2 пропусками `___` (артикль, прийменник, займенник, сполучник).
   * `find_error`: `task_text` німецькою з **однією** чіткою граматичною або лексичною помилкою.
   * `combine_sentences`: два прості речення німецькою + сполучник у дужках, наприклад `(obwohl)` або `(als / wenn)`.
3. `reference_answer` не показується користувачу до перевірки — він зберігається на бекенді як орієнтир.

### 5.5. Перевірка відповіді та мапінг у FSRS (1–4)

Оцінка граматики (`grammar_score`) і рейтинг кожного слова (`word_ratings`) розділені: граматична помилка в порядку слів не повинна обнуляти FSRS-прогрес правильно згаданого слова.

**JSON-схема відповіді LLM при перевірці:**

```json
{
  "is_correct": false,
  "grammar_score": 65,
  "corrected_answer": "Ich bin zu spät zum Treffen gekommen, weil der Zug Verspätung hatte.",
  "word_ratings": [
    {
      "word_id": 14,
      "word_de": "das Treffen",
      "fsrs_rating": 4,
      "note_ua": "Правильний рід і злиття прийменника zum"
    },
    {
      "word_id": 29,
      "word_de": "die Verspätung",
      "fsrs_rating": 3,
      "note_ua": "Слово правильне, але іменник написаний з малої літери"
    }
  ],
  "errors": [
    {
      "wrong_part": "weil der Zug hatte Verspätung",
      "correct_part": "weil der Zug Verspätung hatte",
      "explanation_ua": "Після сполучника weil дієслово завжди переноситься в кінець підрядного речення."
    }
  ],
  "youtube_topic": "Порядок слів у реченні з weil німецька B1",
  "summary_ua": "Лексику згадав точно, але підвів порядок слів у підрядному реченні."
}
```

| Рейтинг FSRS | Назва | Критерій для LLM |
| ----- | ----- | ----- |
| **1** | `Again` | Користувач не згадав слово, пропустив його, переплутав значення або вжив іншу лексему. |
| **2** | `Hard` | Слово вгадано, але є помилка в артиклі/роді (`der/die/das`), множині, керуванні або груба орфографічна помилка. |
| **3** | `Good` | Слово вжито правильно за змістом і формою; допускається дрібна описка (регістр, пропущений умляут без зміни значення). |
| **4** | `Easy` | Бездоганне вживання слова, артикля та форми в граматично чистому реченні. |

**Додаткові правила перевірки:**

* **Античит на бекенді:** якщо користувач скористався підказкою (`used_hint = True`), бекенд примусово обмежує оцінку: `fsrs_rating = min(fsrs_rating, 2)` (максимум `Hard`).
* **Синонімічні варіанти:** у System Prompt перевірки закріплено правило приймати будь-які граматично правильні альтернативні формулювання, якщо вони точно передають зміст і використовують цільові слова, навіть якщо вони відрізняються від `reference_answer`.

## 6. Формули спайдерплоту (0–100, де 100 = впевнений B1)

Для мовних осей застосовується **ваговий коефіцієнт рівня**, щоб ідеальне виконання вправ рівня A1 не давало 100 балів на шкалі B1:

* `A1` — коефіцієнт $0.35$ (максимум ~35 балів)
* `A2` — коефіцієнт $0.70$ (максимум ~70 балів)
* `B1` — коефіцієнт $1.00$ (максимум 100 балів)

### 6.1. Словник (`vocab_score`)

Орієнтир активного закріпленого словника рівня B1 — **1500 слів** зі стабільністю FSRS від 21 дня.

```python
# Внесок кожного слова від 0 до 1 залежно від FSRS stability (поріг закріплення — 21 день)
effective_words = sum(min(1.0, card.stability / 21.0) for card in user_cards)

# Квадратний корінь дає відчутний прогрес на старті, але 1.0 досягається на 1500 словах
volume_part = min(1.0, effective_words / 1500.0) ** 0.5

# Якість пригадування (частка оцінок Good/Easy за останні 30 днів)
recall_part = good_or_easy_count_30d / max(1, total_reviews_30d)

vocab_score = round(100 * (0.75 * volume_part + 0.25 * recall_part))
```

### 6.2. Граматика (`grammar_score`)

Розраховується за останніми **40 вправами** з урахуванням рівня складності та покриття різних тем.

```python
level_weight = {"A1": 0.35, "A2": 0.70, "B1": 1.0}

weighted_scores = [
    attempt.grammar_score * level_weight[attempt.level]
    for attempt in last_40_attempts
]
base_grammar = sum(weighted_scores) / max(1, len(weighted_scores))

# Захист від накрутки на одній темі: 100% множник при покритті >= 6 різних тем
unique_topics = len({a.grammar_topic for a in last_40_attempts})
coverage_factor = min(1.0, unique_topics / 6.0)

grammar_score = round(base_grammar * (0.7 + 0.3 * coverage_factor))
```

### 6.3. Стабільність (`consistency_score`)

Не залежить від рівня — 100 балів доступні навіть на A1 за регулярну практику без боргів у FSRS.

```python
# 60% — регулярність (12 активних днів із 14 = 100%, 2 вихідні допустимі)
days_ratio = min(1.0, active_days_last_14d / 12.0)

# 40% — відсутність боргів у FSRS (слова, прострочені більш ніж на 24 години)
overdue_ratio = overdue_words_24h / max(1, total_active_words)
backlog_health = max(0.0, 1.0 - overdue_ratio)

consistency_score = round(100 * (0.6 * days_ratio + 0.4 * backlog_health))
```

### 6.4. Шрайбен (`writing_score`) та Хьорен (`listening_score`)

У MVP API повертає заглушку зі статусом `coming_soon`:

```json
{ "axis": "writing", "score": 0, "status": "coming_soon" }
```

У Фазах 2–3 підключається аналогічний розрахунок: середній бал останніх 10 завдань (для Шрайбену — граматика, структура, формальність, привітання/прощання; для Хьорену — точність відповідей), помножений на `level_weight`.

## 7. Теми оформлення Mini App (Dark / Light / Auto)

Mini App підтримує три режими оформлення: **Темна (`dark`)**, **Світла (`light`)** та **Автоматична (`system`)**, яка за замовчуванням зчитує поточну колірну схему з `Telegram.WebApp.colorScheme`.

### 7.1. Колірна палітра через CSS-змінні

Теми перемикаються через атрибут `data-theme="dark"` або `data-theme="light"` на кореневому елементі `<html>`:

```css
:root[data-theme="dark"] {
  --bg-primary: #000000;
  --bg-surface: #141414;
  --border-subtle: rgba(255, 255, 255, 0.14);
  --text-primary: #FFFFFF;
  --text-secondary: #A0A0A0;
  --accent: #3B82F6;
  --accent-fill: rgba(59, 130, 246, 0.25);
}

:root[data-theme="light"] {
  --bg-primary: #FFFFFF;
  --bg-surface: #F5F5F7;
  --border-subtle: rgba(0, 0, 0, 0.12);
  --text-primary: #000000;
  --text-secondary: #555555;
  --accent: #2563EB;
  --accent-fill: rgba(37, 99, 235, 0.22);
}
```

### 7.2. Інтеграція з Telegram WebApp SDK та уникнення блимання

* **Системна шапка Telegram:** при кожній зміні теми викликаються методи `Telegram.WebApp.setHeaderColor(bgColor)` та `Telegram.WebApp.setBackgroundColor(bgColor)` (`#000000` для темної або `#FFFFFF` для світлої), щоб верхня панель Telegram збігалася з фоном застосунку.
* **Миттєвий старт без FOUC:** останній вибраний режим кешується в `localStorage` і застосовується в інлайн-скрипті `index.html` ще до монтування React-дерева.
* **Синхронізація між пристроями:** вибір користувача відправляється через `PATCH /users/settings` (поле `theme`) та зберігається в таблиці `users`, щоб налаштування залишалося однаковим на смартфоні й у десктопному Telegram.

### 7.3. Динамічна адаптація спайдерплоту (Chart.js)

Оскільки Chart.js рендерить графік на `<canvas>`, CSS-змінні на нього не діють напряму. При перемиканні теми конфігурація `Radar Chart` оновлюється динамічно:

| Параметр Chart.js | Темна тема (`dark`) | Світла тема (`light`) |

| `scales.r.pointLabels.color` (назви осей) | `#FFFFFF` | `#000000` |
| `scales.r.ticks.color` (підписи шкали 0–100) | `#A0A0A0` | `#555555` |
| `scales.r.grid.color` (концентрична сітка) | `rgba(255, 255, 255, 0.20)` | `rgba(0, 0, 0, 0.15)` |
| `scales.r.angleLines.color` (промені осей) | `rgba(255, 255, 255, 0.20)` | `rgba(0, 0, 0, 0.15)` |
| `datasets[0].borderColor` (контур полігону) | `#3B82F6` | `#2563EB` |
